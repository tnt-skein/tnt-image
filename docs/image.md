# Изображения

`tnt-image` — размер, обрезка, перевод формата, качество, поворот по метке
ориентации, удаление метаданных и превью программой ImageMagick,
запущенной `tnt-process`: картинку разбирает отдельный процесс со сроком
и пределом памяти, узел не стоит, а отказ — пара `nil, err` с родом.

```lua
local image = require('tnt.image')

local images = image.new()

images:inspect(photo)                                              --> { format = 'jpeg', width = 3000, height = 4000, orientation = 6 }
images:thumbnail(photo, { width = 256, height = 256, format = 'webp' })   --> { data = 'RIFF…', format = 'webp', width = 256, height = 256 }
images:transform(photo, { resize = { width = 1200 }, format = 'webp', quality = 80 })
--> { data = 'RIFF…', format = 'webp', width = 1200, height = 1600 }
images:transform('<svg xmlns="http://www.w3.org/2000/svg"/>')
--> nil, magick: данные — не изображение: сигнатура не jpeg, png, gif, webp, avif
```

Здесь и ниже `photo` — снимок телефона: JPEG 4000×3000, записанный лёжа,
с меткой ориентации 6 — «повернуть на четверть по часовой». Всё сверено
с ImageMagick 7.1.1-43 (Debian 13) и 6.9.12-98 (Ubuntu 24.04) — стендом
`make image-up`.

## Зачем пакет

Аватар, обложка статьи, превью ссылки — всё это картинка, которую
прислал посетитель и которую надо уменьшить, обрезать и перевести
в формат, который браузер отдаёт быстро. Своего для этого у Tarantool
нет, а делать это прямо в коде обработчика опасно по трём причинам,
и пакет закрывает каждую.

1. **Разбор картинки — самый опасный ввод узла.** Файл присылает
   посетитель, а разборщики форматов написаны на C. Здесь разбирает
   отдельный процесс: падение разборщика на злом файле — отказ `signal`,
   а не упавший узел.
2. **Узел не ждёт.** Уменьшение снимка в 25 мегапикселей с поворотом
   по метке идёт секунду с небольшим. Процесс ждётся через `popen`,
   соседние файберы в это время работают.
3. **Пределы — до разбора, а не после.** GIF в 29 байт просит кадр
   30 000×30 000 — это 7 ГБ точек. Размер входа проверяется до запуска,
   сторона и число точек — по заголовку, до того как программа развернёт
   картинку, а у самого разбора есть предел памяти и срок.

Сверх этого пакет даёт то, чего у программы нет: формат входа
узнаётся по сигнатуре и называется программе явно, отказ — пара с родом
по словам программы, а итог сверяется с заказанным форматом.

Зависимости: [`tnt-process`](https://github.com/tnt-skein/tnt-process)
(запуск и отказ процесса), [`tnt-fs`](https://github.com/tnt-skein/tnt-fs)
(временный каталог запуска), [`tnt-clock`](https://github.com/tnt-skein/tnt-clock)
(срок вызова), [`tnt-must`](https://github.com/tnt-skein/tnt-must)
(проверки аргументов) и [`tnt-external`](https://github.com/tnt-skein/tnt-external)
(часы срока — внешняя зависимость, подменяемая в проверках). На машине —
ImageMagick 7 (программа `magick`) либо 6 (`convert`).

## Почему ImageMagick и почему процессом

Выбирали из двух путей: системная библиотека через FFI (libvips либо
MagickWand) или программа, запущенная процессом. Библиотека выигрывает
только запуск процесса: осмотр заголовка отдельным процессом идёт на стенде
около 5 мс.

- **FFI работает в потоке узла.** Вызов в C не уступает файбер: пока
  разбирается снимок, узел не отвечает никому — ни запросам, ни
  проверке живости, ни репликации.
- **Падение библиотеки — падение узла.** Разборщики картинок — постоянный
  источник уязвимостей, и злой файл, уронивший разборщик в процессе
  узла, роняет весь узел. Отдельный процесс падает один.
- **Остановить можно только процесс.** Разбор, начатый в потоке узла,
  не прервать ни по сроку, ни по памяти. Процесс убивается по сроку
  вместе с группой, а пределы памяти и стороны держит сама программа.
- **Что есть на машине развёртывания.** Программа ImageMagick — пакет
  `imagemagick` из основного хранилища Debian и Ubuntu. Библиотека
  для FFI — это ещё и выпуск с точным именем (`libMagickWand-7.Q16.so.10`
  против `libMagickWand-6.Q16.so.7`), разный от дистрибутива
  к дистрибутиву.

ImageMagick, а не программа `vips` из libvips, по двум причинам. Всё
преобразование — одна команда: поворот, обрезка, размер, метаданные
и запись идут одним запуском, а `vips` делает одно действие за запуск,
и цепочка стала бы тремя-четырьмя процессами с промежуточными файлами.
И пределы — ключи самой программы (`-limit`), проверенные здесь на обоих
выпусках.

Выпусков два, и пакет работает с обоими: в Debian 13 стоит седьмой
(программа `magick`), в Ubuntu 24.04 — шестой (только `convert`). Пакет
ищет `magick`, а без него `convert`. Ставят так же, как на стенде:

```sh
apt install imagemagick libmagickcore-7.q16-10-extra    # Debian 13
apt install imagemagick libmagickcore-6.q16-7-extra     # Ubuntu 24.04
brew install imagemagick                                 # macOS, для разработки
```

Что сборка умеет писать, показывает `magick -list format` (`convert -list
format`): у обоих выпусков стенда AVIF только читается, и заказанный
AVIF — отказ `unsupported`.

## Как пользоваться

```lua
local image = require('tnt.image')

local images = image.new({
    program = nil,                    -- magick, а без него convert; либо путь
    path = '/usr/local/bin:/opt/homebrew/bin:/usr/bin:/bin',   -- где искать
    timeout = 30,                     -- срок вызова, секунд
    temp_dir = nil,                   -- где заводить временные каталоги; по умолчанию системный
    max_bytes = 20 * 1024 * 1024,     -- предел входа и итога, байт
    max_side = 10000,                 -- предел стороны, точек
    max_pixels = 25000000,            -- предел точек входа
    memory = 512 * 1024 * 1024,       -- память программы под точки, байт
})
```

Всё выше — умолчания, и `image.new()` без настроек даёт тот же клиент.
Программа при сборке не ищется: узел, на который ImageMagick поставят
позже, не требует пересборки клиента, а её отсутствие — отказ у вызова:

```lua
image.new({ path = '/nowhere' }):transform(photo)
--> nil, программы magick и convert не найдены в /nowhere
```

Обложка статьи — полоса 1200×630 из середины снимка:

```lua
images:transform(photo, {
    crop = { x = 0, y = 1200, width = 3000, height = 1575 },
    resize = { width = 1200 },
    format = 'jpeg',
    quality = 82,
})
--> { data = '\xFF\xD8\xFF…', format = 'jpeg', width = 1200, height = 630 }
```

Картинку от посетителя, которую только сохраняют, стоит хотя бы раз
провести через `transform` без действий: метка ориентации применится,
метаданные с координатами съёмки уйдут, а не-изображение и повреждённый
файл получат отказ до того, как лягут на диск.

### Что умеет клиент

| Вызов | Что отдаёт |
|---|---|
| `image.new(options)` | клиент (`TntImageClient`) |
| `images:inspect(data, opts)` | `{ format, width, height, orientation }` — по заголовку, точки не читаются |
| `images:transform(data, opts)` | `{ data, format, width, height }` — итог преобразования |
| `images:thumbnail(data, opts)` | то же: рамка заполнена, лишнее обрезано по центру |
| `image.format(data)` | формат по сигнатуре без запуска программы; `nil` — не изображение |
| `image.INVALID` … `image.FAILED` | роды отказа — см. «Отказ» |
| `image.JPEG` … `image.AVIF` | форматы: `jpeg`, `png`, `gif`, `webp`, `avif` |
| `image.COVER`, `image.INSIDE` | как уместить в рамку: заполнить либо вписать |
| `image.PATH`, `image.DEFAULT_*` | умолчания настроек |

Всё, что может отказать, отвечает парой `nil, err`. У каждого вызова
своя настройка `timeout` — срок этого вызова вместо срока клиента.

## Отказ

`err` — таблица с родом, и читается она как строка: `tostring(err)`,
`'причина: ' .. err` и `json.encode` дают текст.

| Род | Когда | Поля сверх `kind`, `program`, `message` |
|---|---|---|
| `invalid` | не изображение: сигнатура не JPEG, PNG, GIF, WebP и не AVIF | — |
| `corrupt` | повреждено: разборщик отказал либо пожаловался на порчу данных | `reason`, `code`, `stderr` |
| `too_large` | больше предела: байтов входа или итога, стороны, точек, памяти программы | у отказа программы — `reason`, `code`, `stderr`; у итога сверх предела — `stderr` |
| `unsupported` | формат программе не по силам: нет разборщика либо кодировщика, запрет политики, итог не в заказанном формате | `reason`, `stderr`; у отказа программы — и `code` |
| `outside` | область обрезки начинается за краем изображения | — |
| `missing`, `denied` | программы нет либо она не запускается | — |
| `timeout` | срок вызова вышел; процесс убит вместе с группой | у отказа программы — `stdout`, `stderr` |
| `signal` | процесс убит сигналом: разборщик упал либо его убила система | `signal`, `stdout`, `stderr` |
| `failed` | прочее: программа отказала не из-за изображения, ответ не разобран | у отказа программы — `reason`, `code`, `stderr`; у неразобранного ответа — `stdout`, `stderr` |

```lua
images:transform(photo:sub(1, math.floor(#photo / 2)))
--> nil, magick: изображение повреждено (Premature end of JPEG file)
images:transform(gif)          -- 29 байт, заголовок 30000×30000
--> nil, magick: изображение 30000×30000 больше предела стороны 10000
images:transform(photo, { format = 'avif' })
--> nil, magick: формат avif программе не по силам (итог не в нём)
images:transform(photo, { crop = { x = 3000, y = 0, width = 100, height = 100 } })
--> nil, magick: область обрезки 100x100+3000+0 вне изображения 3000×4000
images:transform(photo, { timeout = 0.05 })
--> nil, программа magick не уложилась в срок 0.05 с
image.new({ memory = 64 * 1024 * 1024 }):transform(photo, { resize = { width = 600 } })
--> nil, magick: изображение не уместилось в пределы программы (cache resources exhausted)
```

Отказ временного каталога запуска — место кончилось, нет прав на
`temp_dir` — приходит отказом `tnt-fs` как есть, со своими родами
(`full`, `denied`, `missing`) и своим текстом.

`reason` — первое сообщение программы без её имени, файла и места
в исходниках: по нему видно, что именно она сказала, а по роду — что
с этим делать. В скобках текста отказа стоит оно же; программа, которая
ничего не сказала, — `без пояснения`, а итог не в заказанном формате —
`итог не в нём`: на заказ формата без кодировщика оба выпуска стенда
молчат. `invalid`, `corrupt`, `too_large` и `outside` — ответ
посетителю: картинка не годится. `missing`, `unsupported` и `failed` —
забота оператора: программы нет или она собрана без нужного формата.

Исключение — только ошибка программиста, и показывает оно на строку
вызывающего:

```lua
images:transform(photo, { crop = { width = 100, height = 100, x = 10 } })
--> настройки.crop: края x и y задаются вместе, а без обоих область стоит по центру
images:transform(photo, { resize = { width = 64, fit = 'cover' } })
--> настройки.resize: рамке cover нужны и ширина, и высота
images:transform(photo, { quality = 101 })
--> настройки.quality — число от 1 до 100, а не 101
image.new({ max_side = 1.5 })
--> настройки.max_side — целое число, а не 1.5
```

## Преобразование: `transform`

```lua
images:transform(data, {
    orient = true,        -- повернуть по метке ориентации; по умолчанию да
    crop = { x = 10, y = 20, width = 600, height = 400 },   -- область; без x и y — по центру
    resize = { width = 300, height = 200, fit = 'inside', enlarge = false },
    strip = true,         -- удалить метаданные; по умолчанию да
    format = 'webp',      -- формат итога; по умолчанию тот же, что у входа
    quality = 80,         -- 1–100, только у форматов с потерями
    timeout = 10,         -- срок вызова
})
```

- **Порядок один**, какой бы ни был порядок ключей: поворот по метке,
  обрезка, размер, удаление метаданных, запись. Поворот первым — иначе
  область обрезки считалась бы в координатах, которых человек на экране
  не видел: у снимка с меткой 6 записано 4000×3000, а показывают 3000×4000.
  С `orient = false` края области считаются в записанных координатах.
- **Обрезка.** С `x` и `y` — область с левого верхнего угла; без них —
  область по центру. Область, вылезшая за край, обрезается краем;
  область, начатая за краем, — отказ `outside`: от неё не осталось бы
  ни точки.
- **Размер с сохранением пропорций.** `fit = 'inside'` (по умолчанию)
  вписывает в рамку; сторона без значения не ограничена: `{ width = 300 }` —
  ширина 300, высота по пропорции. `fit = 'cover'` заполняет рамку
  и обрезает лишнее по центру — ему нужны обе стороны. Меньшее рамки
  не увеличивается, пока не сказано `enlarge = true`: иначе аватар 64×64
  раздулся бы до размытого 256×256.
- **Метаданные.** `strip` удаляет EXIF с координатами съёмки и моделью
  телефона, комментарии и профили. Метка ориентации, применённая поворотом,
  тоже уходит: итог стоит как надо и без неё.
- **Формат и качество.** Итог — в `format`, а без него в формате входа.
  Качество уходит программе только у JPEG, WebP и AVIF: у PNG ImageMagick
  читает то же число уровнем сжатия, и `quality = 80` там значило бы
  другое. У JPEG нет прозрачности, и прозрачное ложится на белое — без
  этого программа положила бы его на чёрное.
- **Размеры итога** программа называет сама, отдельного запуска ради
  них нет.

## Превью: `thumbnail`

```lua
images:thumbnail(photo, { width = 256, height = 256, format = 'webp', quality = 70 })
--> { data = 'RIFF…', format = 'webp', width = 256, height = 256 }
```

То же, что `transform` с `resize = { width, height, fit = 'cover' }`:
рамка заполнена, лишнее обрезано по центру, метка применена, метаданные
удалены. Картинка меньше рамки не увеличивается — превью тогда меньше
рамки, но без размытых точек.

## Осмотр: `inspect`

```lua
images:inspect(photo)
--> { format = 'jpeg', width = 3000, height = 4000, orientation = 6 }
```

Программа читает только заголовок (`-ping`), точки не разворачиваются,
и пределы стороны и точек тут не проверяются: осмотр как раз и нужен,
чтобы узнать размер до преобразования — например, отказать в аватаре
меньше 128 точек. Ширина и высота — так, как картинку покажут, после
поворота по метке; `orientation` — номер метки EXIF, 1 — поворота нет.

Формат без запуска программы — `image.format(data)`: сигнатура, ничего
больше. Файл, чья сигнатура годится, всё равно может оказаться
повреждённым — это скажет только программа.

## Пределы

| Предел | Где держится | Род отказа |
|---|---|---|
| `max_bytes` — вход | до запуска программы | `too_large` |
| `max_bytes` — итог | вывод программы больше предела: процесс убит | `too_large` |
| `max_side`, `max_pixels` | по заголовку, до разбора точек | `too_large` |
| `max_side` — итог | ключ программы `-limit width/height`: увеличение сверх предела | `too_large` |
| `memory` | ключ программы `-limit memory`, файлы запрещены (`map 0`, `disk 0`) | `too_large` |
| `timeout` | один срок на вызов, процесс убит вместе с группой | `timeout` |

Умолчания согласованы между собой: точка в памяти ImageMagick стоит восемь
байт, поворот по метке держит две копии кадра, и 25 мегапикселей
с поворотом укладываются в 512 МиБ, а в 256 — уже нет (проверено на обоих
выпусках). Поднимая `max_pixels`, поднимают и `memory`.

Файлы программе запрещены нарочно: без `map 0` и `disk 0` картинка,
не влезшая в память, молча легла бы кэшем точек на диск узла и шла бы
минутами. Преобразование занимает одно ядро (`-limit thread 1`): узел
делит машину с программой, и процессор нужен ему самому.

## Что ImageMagick делает не так

Сверено на 7.1.1-43 и 6.9.12-98; каждый пункт закрыт в пакете и закреплён
проверкой — двойником в `test/` и живой проверкой против стенда.

| Что | Как у программы | Как в пакете |
|---|---|---|
| формат входа | угадывает по содержимому, узнаёт и сценарии: SVG с внешними ссылками, MVG, MSL, текст `@файл` | формат по сигнатуре, названный явно (`jpeg:-`), всё прочее — `invalid` до запуска |
| обрезанный JPEG | предупреждение «Premature end of JPEG file», недостающее дорисовано серым, код 0; `-regard-warnings` делает его отказом у 6.9, но не у 7.1 | предупреждение о порче — отказ `corrupt` на обоих |
| мусор после конца JPEG | предупреждение «extraneous bytes», картинка цела | не отказ: камеры пишут его часто |
| итог в формате без кодировщика (`avif:-`) | 6.9: молча пишет итог в формате входа, код 0; 7.1: пустой вывод, код 0; оба без единого сообщения | сигнатура итога сверяется с заказанной, отказ `unsupported` |
| `-ping` при `-limit width` | размеры отдаёт, предела не проверяет | размеры сверяются с пределами в пакете |
| `-limit area` | не отказывает: кадр сверх площади идёт дальше | предел точек — по заголовку в пакете |
| сторона сверх `-limit width` | 7.1: «width or height exceeds limit»; 6.9 на PNG: «exceeds user limit in IHDR» и «Invalid IHDR data» | оба — `too_large`, пределы разбираются раньше порчи |
| запрет политики `policy.xml` | «not allowed by the security policy» у обоих, у прежних выпусков шестого — «not authorized» | оба — `unsupported` |
| анимация | в итог идут все кадры | читается только первый кадр (`[0]`) |
| JPEG из прозрачного PNG | прозрачное — чёрным | прозрачное — белым (`-alpha remove`) |
| временные файлы | вход с трубы копирует в `/tmp` и, убитый по сроку, не убирает | у каждого запуска свой временный каталог (`MAGICK_TEMPORARY_PATH`), он сносится при всяком исходе |

Политику дистрибутива (`/etc/ImageMagick-7/policy.xml` в Debian 13) пакет
не заменяет, а дополняет: она закрывает программе сеть и чтение `@файла`,
а пакет не даёт ей выбрать разборщик самой.

## Ничто не держит узел

Запуск, запись входа, чтение вывода и ожидание — средства `popen`
через `tnt-process`, все они уступают файбер. Программа получает
окружение из пяти переменных, собранных пакетом, — каталоги поиска,
английский язык сообщений (`LANG=C`, `LC_ALL=C`: разбор знает один язык)
и временный каталог, — а не окружение узла: пароли узла ей ни к чему.

## Чем пришлось поступиться

- **Два запуска на преобразование.** Первый читает заголовок ради
  пределов и области обрезки, второй преобразует. Цена — ещё один процесс,
  около 5 мс (замер на стенде); выигрыш — картинка сверх предела
  не разворачивается в памяти вовсе.
- **Картинка целиком в памяти узла.** Вход и итог — строки, и оба
  не больше `max_bytes`. Потокового преобразования нет: для картинок
  с пределом в десятки мегабайт оно не окупается.
- **Анимация не сохраняется.** Из GIF и WebP берётся первый кадр —
  превью анимации это и нужно, а файл в тысячу кадров иначе стоил бы
  тысячи преобразований.
- **Вместе с метаданными уходит профиль цвета.** Снимок в широком охвате
  (Display P3) после `strip` показывается чуть тусклее. Кому это важно,
  задают `strip = false` и чистят метаданные сами.
- **Мусор после конца JPEG — не порча.** «Extraneous bytes» пропускаются:
  точки целы. Прочие жалобы разборщика на данные — отказ, даже если
  программа что-то дорисовала.
- **Порча и поломка различаются по словам программы.** Код выхода
  говорит только «не получилось», и сообщение ImageMagick об ошибке, не
  узнанное как предел, запрет или беда среды, читается порчей: программа
  разбирает только наши данные названным разборщиком. Ненулевой код без
  сообщения ImageMagick — `failed`.
- **AVIF только читается** на обоих выпусках стенда: кодировщика в их
  сборках нет, и заказ AVIF — отказ `unsupported`.
- **Одно ядро на преобразование.** Большой снимок на многоядерной машине
  шёл бы быстрее, но за счёт процессора, нужного узлу.

## Стенд и проверки

```sh
make image-up                          # test/stand/image.sh: ImageMagick 7.1 из Debian 13 в контейнере
IMAGE_STAND_VERSION=6 make image-up    # ImageMagick 6.9 из Ubuntu 24.04
make test
make image-down
```

Проверки в `test/` идут на программе-двойнике — сценарии оболочки, который
отвечает записанным выводом настоящих выпусков и запоминает аргументы,
вход, окружение и временный каталог; запускает его настоящий `tnt-process`.
Живые проверки (`image_live_test.lua`) — против стенда: уменьшение
и увеличение, обрезка областью, у края и по центру, поворот по метке EXIF
с проверкой точек, удаление метаданных, WebP и качество, превью, JPEG
из прозрачного PNG, первый кадр анимации, AVIF без кодировщика,
не-изображение и повреждённые JPEG, PNG, GIF и WebP, GIF-бомба, пределы
памяти, стороны и итога, срок и пустой каталог после вызовов. Картинки
рисует программа стенда, метка EXIF вписывается руками: двоичных образцов
в репозитории нет. Обе программы выпусков проходят их целиком.

На стенде программа живёт в контейнере, и процесс, убитый по сроку, — это
`docker exec` на хозяине: программа в контейнере дорабатывает сама. Срок
и отказ по нему проверяются честно, убийство программы — нет.

Без стенда живые проверки пропускаются: гейты не должны зависеть
от докера. Проверок — 66, из них 13 живых; покрытие строк — 100 %,
убитых мутантов — 100 % (363 мутанта в шести модулях).
